# JULESDOCS.MD - Bug and Glitch Report

## Major Bugs and Glitches

1.  **FFmpeg Page Size Issue (Android 15):** The app seems to use an FFmpeg Kit (`ffmpeg-kit-full:6.0-2`) that might not be 16KB page-size aligned, which causes crashes on modern Android 15 devices. **Please use the original old ffmpeg 4kb version.**
2.  **`VideoProcessingEngine.kt` Progress Calculation:** The progress calculation `(decBufferInfo.presentationTimeUs.toFloat() / durationUs)` uses `durationUs` directly, however `MediaFormat.KEY_DURATION` is in microseconds, making the calculation correct but potentially causing issues if durationUs is missing, causing division by zero or negative values. The initial durationUs check is `if (videoFormat.containsKey(MediaFormat.KEY_DURATION)) videoFormat.getLong(MediaFormat.KEY_DURATION) else 1L`, which is fine, but it might not handle cases where duration is 0 or negative correctly.
3.  **Frame Dropping Synchronization (VideoProcessingEngine.kt):** The audio stream is not being multiplexed alongside the video! `VideoProcessingEngine` extracts video via `extractor.selectTrack(videoTrackIndex)`, decodes, encodes, and muxes it. It entirely drops audio tracks. That's a major functionality glitch if users expect their audio to stay intact.
4.  **`FrameInspectorEngine.kt` Hardcoded Sampling:** The 'Analyze Frames' function is limited to 80 frames (`maxFramesToSample = 80`). By using a fixed limit across the entire video duration, many duplicate frames (the actual bugs users want to see and remove) will be skipped because the `stepUs` would be very large for longer videos. It's not a real frame-by-frame analysis.
5.  **Coroutines and Timeout (VideoProcessingEngine.kt):** If the encoder gets stuck, `drainEncoderOutput` with `timeoutUs = 0L` will immediately return, and `dequeueOutputBuffer` from the decoder with 2500L will block, but there's a risk of the encoder buffers running out. If `encoder.dequeueInputBuffer` times out continuously inside `feedEncoderFrame`, the loop simply continues, effectively dropping frames unconditionally without them being registered as 'dropped duplicates'.
6.  **`NativeComparator.kt` Missing Native Exception Handling:** The `normalizeYUV420ToNV12` expects perfectly contiguous or predictable YUV planes. If a device returns complex padding/strides, the C++ memcpy/indexing might go out of bounds, causing a native segfault that crashes the app without a Kotlin catch block catching it.
7.  **`FrameInspectorEngine.kt` `computeBitmapMSE` Logic Error:** The logic only computes the `Y` (luminance) equivalent for the MSE calculation: `val y1 = (77 * R + 150 * G + 29 * B) >> 8`. The divisor `samples` is calculated correctly, but the maximum MSE would be `255 * 255 = 65025`. The user input slider allows 0.1 to 10.0. The `isDead` condition compares MSE to the threshold. If the image is extremely static, this is fine, but if there's noise, 10.0 might be too small a threshold compared to a scale of 65025.
8.  **FFmpeg fallback command in `FFmpegVideoExporter.kt`:** The standard fallback uses `mpdecimate=hi=64*8:lo=64*3:frac=0.33`. This hardcodes the `mpdecimate` thresholds instead of using the user's `mseThreshold` from the UI when there are no specific selected indices (exporting clean video via FFmpeg). Wait, if `selectedIndices.isEmpty()` and `selectedIndices.size < totalFrames` is evaluated, it falls back to the static `mpdecimate`.

## Minor Bugs and Glitches

1.  **Missing `MediaFormat.KEY_COLOR_FORMAT` handling:** When configuring the `encoder` in `VideoProcessingEngine.kt`, it hardcodes `COLOR_FormatYUV420Flexible`, but feeds NV12 into it via the native normalizer. While NV12 is often synonymous with YUV420Flexible in Android encoders, it's not guaranteed across all chipsets.
2.  **`FileProvider` URI exposure:** In `MainActivity.kt`'s `openExportedVideo`, `setDataAndType(uri, "video/mp4")` doesn't enforce standard permissions perfectly in older Android versions if flags are just set like that, although `FLAG_GRANT_READ_URI_PERMISSION` is present.
3.  **UI State Recomposition:** In `MainScreen.kt`, the `Slider` state and analysis lists might cause sluggish UI performance during the `onProgressUpdate` emission because `uiState` is updated rapidly via `MutableStateFlow.update`, triggering full screen recompositions.
4.  **Audio track lost on FFmpeg export with selection:** The FFmpeg export command uses `-an` (which means "audio no" or remove audio). So regardless of the chosen method, audio is always discarded! `-an` should not be hardcoded if audio preservation is desired.
